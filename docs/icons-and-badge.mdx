## Icons

flavorizr makes the launcher icons of a flavor from **one source image**, at every size the platform
needs: the legacy mipmaps of Android, the icon sets of iOS and macOS, and the `.ico` of Windows. The
**adaptive icon** of Android is not made from it: it needs its own layers, see
[`adaptiveIcon`](/configuration/android#adaptiveicon), and until a flavor has them a device from Android 8
may show the adaptive icon of `main` instead of the icon of the flavor. Nothing is downloaded and no placeholder is bundled: what flavorizr writes, it makes.

The `icon` of a flavor is, in order of precedence, the `icon` of its platform section and the `icon` of its
`app`:

```yaml
flavors:
  dev:
    app:
      name: "My App Dev"
      icon: "assets/icon/dev.png"          # every platform
    android:
      applicationId: "com.example.app.dev"
      icon: "assets/icon/dev_android.png"  # Android only
```

An `icon` is a path relative to the project that stays inside it, links included. The icons of Android, iOS
and macOS are generated files, owned as **managed** and hashed in the lock, so editing one by hand is a
conflict. The Windows icons are the exception: `windows:icons` is a 2.x processor that is not on the engine
yet, so its `.ico` files are not in the lock, and a run writes them over a hand edit without a conflict. The
output is deterministic: the same sources always give the same bytes. Android flavors can also set an
[`adaptiveIcon`](/configuration/android#adaptiveicon).

### A flavor with no icon

**A flavor with no `icon` gets nothing generated, and builds with the default icon of the project**: the
`main` resources on Android, `AppIcon` on iOS and macOS, `app_icon.ico` on Windows. A flavor builds with
its own icon instead when the project already has one for it: an `AppIcon-<flavor>.appiconset` on iOS and
macOS, and a `windows/runner/resources/<flavor>.ico` on Windows, which is used whoever made it (so it
stays in use after you remove the `icon` of the flavor, until you delete the file and run `apply`).

An icon you put in the project yourself (`src/<flavor>/res`, `AppIcon-<flavor>.appiconset`,
`<flavor>.ico`) is yours: flavorizr points the flavor at it and never deletes it. Once the flavor has an
`icon` (or a badge), the set or the files that flavorizr would write are not yours to keep: on Android, iOS
and macOS a file of the project that the lock does not know is a [conflict](/conflicts) and nothing is
written until you answer, and `windows:icons` writes `<flavor>.ico` over yours.

`generateDummyAssets`, which made placeholder icons in 2.x from assets that it downloaded, is
deprecated and ignored. Remove it: it will be an error in 4.0. `assetsUrl` is an error now, since there is
nothing to download.

### iOS and macOS

`ios:icons` and `macos:icons` make `AppIcon-<flavor>.appiconset` in `ios/Runner/Assets.xcassets` and
`macos/Runner/Assets.xcassets`: every PNG of the set, resized from the source icon, and a `Contents.json`
written in code (the text 2.x wrote, byte for byte). A flavor builds with its own set when it has an `icon` or
a badge, or when the project has an `AppIcon-<flavor>.appiconset` already, and with the `AppIcon` of the
project otherwise. A file of yours in the set stays when the set is removed.

### Removing icons

The icons of a flavor are cleaned with it when you remove the flavor, or when you remove its `icon` and it has
no badge, on Android, iOS and macOS: the files are managed, and a set that is not made anymore is removed
with its folder (a file of yours in it stays). A flavor that loses its icon builds with the `AppIcon` of the
project in that same run.

`windows:icons` is the one processor that makes icons and is not on the engine yet (see
[Command line](/reference/cli#processors-that-are-not-on-the-engine-yet)). It does not track what it writes, so
the `windows/runner/resources/<flavor>.ico` files stay in the project when the `icon`, the badge or the flavor
goes, and `windows:cmake` keeps pointing the flavor at the file while it is there: delete it, and run `apply`,
to go back to the default `app_icon.ico`.

## The launch screen and Android

On iOS a flavor can have a launch screen made from its icon (and its badge): see
[the launch screen](/configuration/ios#the-launch-screen). Android needs nothing generated. From Android 12
the system shows the splash screen with the launcher icon of the flavor, which `android:icons` makes (with its
badge, if it has one), so each flavor already has its own. Older versions show the launch background of the
project, which flavorizr does not touch.

## Icon badge

A badge is a band with the name of the flavor on its icon, to tell a `dev` build from a `prod` one at a
glance.

```yaml
badge: true                       # root default (default: false)
flavors:
  dev:
    app: { name: "App Dev" }
    badge: { label: DEV, color: "#E53935" }
  staging:
    app: { name: "App Staging" }  # inherits: label "STAGING", automatic colour
  prod:
    app: { name: "App" }
    badge: false                  # opt-out
```

| Key | Type | Default | Description |
| --- | --- | --- | --- |
| `badge` (root) | bool | `false` | Whether the flavors have a badge, unless they say otherwise. |
| `badge` (flavor) | bool or map | the root | `true` or a map turns it on for the flavor, `false` off. |
| `label` | string | the flavor name, upper-cased | The text of the badge: 8 characters at most, a longer one is cut to 7 and `…`. |
| `color` | string | from the palette, by the flavor name | The color of the band, as `#RRGGBB`. |
| `icon` (root) | string | | The source icon of the badges when a flavor has no `icon` of its own. |

- `color` is picked from a palette by a stable hash of the name of the flavor, so it is the same in every
  run and on every machine. The text is black or white, whichever has the better contrast: at least 4.5:1
  on every color.
- There are no font or style options.
- The **source icon** of a badge is the first of these that is 512 px or more: the `icon` of the flavor,
  the root `icon`, the larger of the `AppIcon` of the iOS and the macOS project. When there is none, the
  run fails with a hint to set `icon:`. A flavor with a badge has icons made for it even when it has no
  `icon`.
- The band is across the bottom of the icon, with the label in the `arial48` bitmap font. It is drawn at
  each size of the icon, not scaled from a larger one, on the Android legacy mipmaps, the iOS and macOS
  icon sets and the Windows `.ico`. That font has no `…`: a label that was cut is drawn with `...`.
- Changing the label or the color makes the icons again on the next run, and `badge: false` makes the
  icons of the `icon` without it.

### Android

On Android, the band of an adaptive icon is on its foreground, inside the safe zone (the 66 dp circle at
the middle), so that no launcher mask cuts it. The background and the monochrome layer are left as they
are.

Only the icons made from a raster image are badged. A flavor without an `adaptiveIcon` of its own is **not**
badged, and a warning says why, when `main` has `mipmap-anydpi-v26/ic_launcher.xml`: a device from Android 8
shows that adaptive icon (its foreground may be a vector) instead of the legacy mipmaps. Give the flavor a
raster `adaptiveIcon`, or set `badge: false`. A flavor whose `adaptiveIcon` has a vector (`.xml`)
foreground gets no Android icons at all while it has a badge, and a warning says why.

### iOS, macOS and Windows

The band is drawn on the icons of each set at the size of each icon. The icons of a flavor that has a badge
and no `icon` are removed when the badge goes, on Android, iOS and macOS, which track what they write. The
Windows `.ico` of such a flavor stays in the project, since `windows:icons` is a 2.x processor.
