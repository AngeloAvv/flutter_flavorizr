## Icons

flavorizr makes the launcher icons of a flavor from **one source image**, at every size the platform
needs: the legacy mipmaps of Android, the icon sets of iOS and macOS, and the `.ico` of Windows. The
**adaptive icon** of Android is not made from it: it needs its own layers, see
[`adaptiveIcon`](/configuration/android#adaptiveicon), and until a flavor has them a device from Android 8
may show the adaptive icon of `main` instead of the icon of the flavor. Nothing is downloaded and no placeholder is bundled: what flavorizr writes, it makes.

The `icon` of a flavor is, in order of precedence, the `icon` of its platform section and the `icon` of its
`app`:

```yaml
flavors:
  dev:
    app:
      name: "My App Dev"
      icon: "assets/icon/dev.png"          # every platform
    android:
      applicationId: "com.example.app.dev"
      icon: "assets/icon/dev_android.png"  # Android only
```

An `icon` is a path relative to the project that stays inside it, links included. The icons of every
platform (Android, iOS, macOS and Windows) are generated files, owned as **managed** and hashed in the lock,
so editing one by hand is a conflict. The output is deterministic: the same sources, rendered by the same
version of flavorizr, give the same bytes. The lock also records what each icon was made **from** (the bytes
of the source image, the sizes, the badge): a run that finds the same inputs and the file as it recorded
neither renders nor writes it, so a change of the path of the source, or of the library that encodes the
images, writes nothing. See [Inputs of generated files](/reference/lock#inputs-of-generated-files).
Android flavors can also set an [`adaptiveIcon`](/configuration/android#adaptiveicon).

### A flavor with no icon

**A flavor with no `icon` and no badge gets nothing generated, and builds with the default icon of the
project**: the `main` resources on Android, `AppIcon` on iOS and macOS, `app_icon.ico` on Windows, unless the
project has an icon for that flavor already: see [Every case](#every-case).

`generateDummyAssets`, which made placeholder icons in 2.x from assets that it downloaded, is
deprecated and ignored. Remove it: it will be an error in 4.0. `assetsUrl` is an error now, since there is
nothing to download.

### iOS and macOS

`ios:icons` and `macos:icons` make `AppIcon-<flavor>.appiconset` in `ios/Runner/Assets.xcassets` and
`macos/Runner/Assets.xcassets`: every PNG of the set, resized from the source icon, and a `Contents.json`
written in code (the text 2.x wrote, byte for byte). A flavor builds with its own set when it has an `icon` or
a badge, or when the project has an `AppIcon-<flavor>.appiconset` already, and with the `AppIcon` of the
project otherwise.

### Every case

What a flavor gets, by what it has. The **source** of the icons is the `icon` of the platform section or of
the `app` of the flavor. A [badge](#icon-badge) is on when the flavor, or the root, says so. The root `icon`
is **not** an icon of the flavor: it is only where a badge, or a launch screen, finds an image when the flavor
has none of its own. The cases are the same on Android, iOS, macOS and Windows, which make their files with
the same rules.

| Case | What happens |
| --- | --- |
| `icon` is an image, no badge | Icons made from it, whatever its size. |
| `icon` is missing or is not an image, no badge | The run fails (exit `70`) and **writes nothing**. |
| No `icon`, no badge, and no file of the flavor in the project | Nothing is made. The flavor builds with the default icon of the project: the `main` resources on Android, `AppIcon` on iOS and macOS, `app_icon.ico` on Windows. |
| No `icon`, no badge, and the project has a file of the flavor that the lock does not know (`src/<flavor>/res`, `AppIcon-<flavor>.appiconset`, `<flavor>.ico`) | It is yours. The flavor builds with it, and a run leaves it alone while the flavor has no `icon` and no badge: it does not overwrite or delete it. `windows:cmake` points the flavor at `<flavor>.ico` whoever made it. |
| Only a root `icon` (no `icon` of the flavor, no badge) | Nothing is made. |
| Badge, and `icon` is an image of 512 px or more | Icons made from it, with the band. |
| Badge, and no `icon`, or one that is missing, is not an image or is under 512 px | The icon is passed over, **with no error**, and the source is the first image of 512 px or more among the root `icon` and the `AppIcon` of the iOS and macOS projects (the larger one). Icons are made from it, with the band. |
| Badge, and there is no image of 512 px or more anywhere | The run fails with a hint to set `icon:`, and **writes nothing**. |
| The flavor has an `icon` or a badge, and the project has a file where a generated one goes that the lock does not know | A [conflict](/conflicts): you are asked, and nothing is written until you answer. This includes the file of the previous row, once the flavor gets an `icon` or a badge. |
| You edited a generated icon by hand | A [conflict](/conflicts): the run renders it again and asks before it replaces your edit. |
| You remove the `icon` of a flavor that has no badge, or the badge of one that has no `icon`, or the flavor | The generated files are removed, with their folder (a file of yours in it stays). The flavor builds with the default icon of the project in that same run: on iOS and macOS with `AppIcon`, on Windows with `app_icon.ico`. |
| You remove the `icon` of a flavor that still has a badge, or the badge of one that still has an `icon` | The icons are made again, from the source the case says. Nothing is removed. |

On Windows `windows:cmake` points a flavor at its `<flavor>.ico` when `windows:icons` makes one for it, or when
the project has one that the lock does not know. A `<flavor>.ico` that the lock recorded and the flavor no
longer makes is removed, and the flavor builds with `app_icon.ico` again.

On Android a flavor with an `adaptiveIcon` and no `icon` has the layers of the adaptive icon and no legacy
mipmaps, with or without a badge (the band is on the foreground); see [Android](#android) below.

## The launch screen and Android

On iOS a flavor can have a launch screen made from its icon (and its badge): see
[the launch screen](/configuration/ios#the-launch-screen). Android needs nothing generated. From Android 12
the system shows the splash screen with the launcher icon of the flavor, which `android:icons` makes (with its
badge, if it has one), so each flavor already has its own. Older versions show the launch background of the
project, which flavorizr does not touch.

## Icon badge

A badge is a band with the name of the flavor on its icon, to tell a `dev` build from a `prod` one at a
glance.

```yaml
badge: true                       # root default (default: false)
flavors:
  dev:
    app: { name: "App Dev" }
    badge: { label: DEV, color: "#E53935" }
  staging:
    app: { name: "App Staging" }  # inherits: label "STAGING", automatic colour
  prod:
    app: { name: "App" }
    badge: false                  # opt-out
```

| Key | Type | Default | Description |
| --- | --- | --- | --- |
| `badge` (root) | bool | `false` | Whether the flavors have a badge, unless they say otherwise. |
| `badge` (flavor) | bool or map | the root | `true` or a map turns it on for the flavor, `false` off. |
| `label` | string | the flavor name, upper-cased | The text of the badge: 8 characters at most, a longer one is cut to 7 and `…`. |
| `color` | string | from the palette, by the flavor name | The color of the band, as `#RRGGBB`. |
| `icon` (root) | string | | The source icon of the badges when a flavor has no `icon` of its own. |

- `color` is picked from a palette by a stable hash of the name of the flavor, so it is the same in every
  run and on every machine. The text is black or white, whichever has the better contrast: at least 4.5:1
  on every color.
- There are no font or style options.
- The **source icon** of a badge is the first of these that is 512 px or more: the `icon` of the flavor,
  the root `icon`, the larger of the `AppIcon` of the iOS and the macOS project. One that is missing, is
  not an image or is smaller is passed over, with no error. When there is none, the run fails with a hint
  to set `icon:`. A flavor with a badge has icons made for it even when it has no `icon`. The same
  source is the one of the iOS [launch screen](/configuration/ios#the-launch-screen) of a flavor with a badge.
  All of it is in [Every case](#every-case).
- The band is across the bottom of the icon, with the label in the `arial48` bitmap font. It is drawn at
  each size of the icon, not scaled from a larger one, on the Android legacy mipmaps, the iOS and macOS
  icon sets and the Windows `.ico`. That font has no `…`: a label that was cut is drawn with `...`.
- Changing the label or the color makes the icons again on the next run, and `badge: false` makes the
  icons of the `icon` without it.

### Android

On Android, the band of an adaptive icon is on its foreground, inside the safe zone (the 66 dp circle at
the middle), so that no launcher mask cuts it. The background and the monochrome layer are left as they
are.

Only the icons made from a raster image are badged. A flavor without an `adaptiveIcon` of its own is **not**
badged, and a warning says why, when `main` has `mipmap-anydpi-v26/ic_launcher.xml`: a device from Android 8
shows that adaptive icon (its foreground may be a vector) instead of the legacy mipmaps. Give the flavor a
raster `adaptiveIcon`, or set `badge: false`. A flavor whose `adaptiveIcon` has a vector (`.xml`)
foreground gets no Android icons at all while it has a badge, and a warning says why.

### iOS, macOS and Windows

The band is drawn on the icons of each set at the size of each icon, and on every size of the Windows
`.ico`. What happens to the icons when the badge, the `icon` or the flavor goes is in
[Every case](#every-case): on every platform they are removed, or made again when the flavor still has
an `icon` or a badge.
